# codex-weekly-usd

[English](README.en.md) · 简体中文

一个 [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) 插件，只回答一个问题：

> **这个 Codex 账号的额度，按 OpenAI 官方 API 计费，值多少美元？**

商店里已有的用量类插件大多停在 token 数和百分比。这个插件把两者**除一下**，给出美元。

一个凭据同时受**多个窗口**限制（目前是 5 小时 + 一周），同一笔花费同时计入所有窗口，
所以每个窗口各自独立记账、各自估算。

顺带回答第二个问题：**某个模型现在还调不调得通、什么时候恢复？** 见 [模型可用性](#模型可用性)。

## 原理

Codex 每次响应都带着这个账号的额度状态，而每次请求都会产生 token 计数。把两者配对：

```
分子   UsageRecord.Detail 里的 token 数 × 官方价目
分母   该窗口的已用百分比响应头

窗口额度(美元) = 花费 / (已用百分比 / 100)
```

上游 `chatgpt.com/backend-api/codex` 的真实响应头：

```
x-codex-primary-window-minutes:   300      ← 5 小时
x-codex-primary-used-percent:     100
x-codex-secondary-window-minutes: 10080    ← 7 天
x-codex-secondary-used-percent:   63
x-codex-plan-type: team
x-codex-active-limit: premium
```

这些头在 **200 响应上就有**，不是只在 429 限流时才返回。

### ⚠ 窗口按**长度**识别，不按 primary/secondary 标签

这两个标签的含义**变过一次**：5 小时限额回归之前，`primary` 是周窗口、`secondary` 不存在；
之后 `primary` 变成 5 小时窗口，周窗口挪到了 `secondary`。

把 `primary` 当成"那个窗口"会出两种错：周窗口的历史整段丢失，而且**周窗口的 1% 和 5 小时
窗口的 1% 代表的钱差着数量级**，混在同一个校准里平均出来的数毫无意义。所以本插件一律按
`window_minutes` 给窗口建档。

### 两个互相独立的估算器

| 依据 | 算法 | 何时可用 |
|---|---|---|
| `窗口法` | 整窗花费 ÷ 整窗百分比 | 只在插件亲眼看到窗口从 0% 开始时 |
| `步进法` | Σ两次读数间的花费 ÷ Σ百分比步进 | 第一次百分比跳动之后，随时 |

烧掉 3% 以上时优先用**窗口法**——它拿整窗的钱对整窗的百分比，没有归属上的猜测。**步进法**是兜底，它不在乎插件是什么时候装的，所以**中途安装也能收敛**，而不是给出一堆离谱数字。

`confidence`（置信度）反映插件**亲眼看着**消耗掉的额度有多少：≥25 个点为高，≥8 为中，更低为低，第一次跳动之前为无。

**校准样本有上限**（数量 160 条、时效 21 天）。无上限累加的话，套餐调整、窗口语义变化、
模型改价之后，旧证据会永远压过新证据，而"证据量"还会一路涨到几百个点，让置信度**看起来
越来越高、实际越来越错**。有界之后估算会跟着现实走。

### 归属：为什么要挂账

额度头是在上游响应流打开时发出的，描述的是**本次请求计入之前**的状态。所以本次花费先记入 `pending` 挂账，到**下一次**读数才和百分比步进配对。

`attributed_usd` 是最新百分比已经有机会涵盖的花费；未扣挂账的窗口原始总额单独报为 `window_usd_observed`。**窗口法必须用前者**，否则会系统性高估。

### token 口径

CLIProxyAPI 把 OpenAI 的计数器定义为子集关系：

- `CacheReadTokens`、`CacheCreationTokens` **在** `InputTokens` **里面**
- `ReasoningTokens` **在** `OutputTokens` **里面**

所以缓存 token 要从输入桶里**扣出来**按缓存价算，推理 token **绝不**在输出之上再加一遍。任何一个重复计费都会让整体估算虚高。

没有公开缓存写入价的模型，那部分 token 会**折回按新鲜输入计价**，而不是当成免费。

### 上游中途送重置

OpenAI 经常在周期没结束时把额度还回来：**百分比掉回去，但 `reset_at` 不变**。只按
`reset_at` 判断周期翻转会漏掉这种情况，于是重置前的花费仍留在账上、却要除以重置后的
一个很小的百分比——估算直接炸掉。因此**百分比回退也算周期翻转**，并单独计数（面板显示
"周期内重置 N 次"）。

### 别人也在用这个凭据

如果百分比涨了、而本插件这一段没有任何花费，说明有别的客户端在共用该凭据。这种情况下
样本会被跳过（否则会污染校准），同时累加到 `unexplained_percent` 并在面板告警——因为它
同时意味着**本插件的账是少记的**。

### 重启安全

状态是持久化的，重启不会丢窗口。但插件停机期间跑掉的流量**在百分比里、不在账里**——所以重启后第一次读数如果百分比涨了，窗口法的覆盖标记会作废，陈旧挂账会丢弃，而不是拿去和一段它没有造成的百分比步进配对。

## 模型可用性

CLIProxyAPI 的冷却是按「**凭据 × 模型**」的，不是把整个凭据拉黑：上游对每个模型有独立额度，
所以一个凭据完全可以「某个模型已耗尽、其它模型照跑」。

**这带来一种很难查的故障形态**：某个模型的凭据全部同时冷却时，外部表现是「**只有这一个模型用不了**」，
而凭据状态（`auth-files` 里全是 `active`）和上游渠道状态都会显示一切正常。
要定位就只能去翻代理日志里的三处不同位置。

面板顶部的「模型可用性」看板直接回答它：

| 列 | 含义 |
|---|---|
| 状态 | `正常` / `部分冷却` / `全部冷却`，外加「单点凭据」标记 |
| 可用 / 凭据 | 现在能服务该模型的凭据数；**已停用的凭据只列出、不计入容量** |
| 最快恢复 | 第一个凭据解除冷却的倒计时 |
| 各凭据状态 | 每个凭据一枚标签，悬停可见原因、哪个窗口打满、恢复时刻、历史冷却次数 |

两条结构化告警：

- **`model_unavailable`** —— 该模型已无可用凭据，附最快恢复时间。这是「只有这一个模型挂了」的正式命名。
- **`model_single_point`** —— 该模型只剩 1 个可用凭据。它下一次撞 429，整个模型就没了；
  代理自身的任何状态在此之前都不会提示。

判定口径：

- **冷却截止时间取自上游返回的 window reset**，与代理实际使用的是同一个值 —— 取**真正打满的那个窗口**的 reset
  （两个都满时取较晚的一个），而不是「下一个到期的窗口」。
- **额度用尽（`credits_depleted`）时百分比可能全都不满**，没有窗口可读，就退而取最近的一个 reset 并**标记为估计值**。
- **一次成功的请求立即解除冷却标记**，不管记录的截止时间还剩多久 —— 上游经常提前放行。
- **没有额度信号的失败不算冷却**（断连、参数错误等），只计入失败数。
- 同一次冷却期内的重复 429 记为**一次**，因为统计的是「模型断了几次」，不是「弹回多少个请求」。

## 凭据轮换（可选，默认关闭）

轮换器维持固定数量的凭据处于启用状态，并在成员**快耗尽之前**把它换掉。

为什么是「池」而不是「一个」：代理的 fill-first 选择器在一个凭据被拒时，会**在同一个请求内**改用下一个
启用的凭据。所以只要替补已经在池子里，换人对调用方完全无感；而池子里只有一个，就根本没有换人的余地。
默认 `keep_enabled: 2`。

**这是本插件唯一会写自身数据目录之外文件的部分**，所以默认关闭，并且带 `dry_run`——照常判断、照常记录，
但不真的改写凭据。建议先空跑一段时间，看着日志确认无误再打开。

### 什么时候换

满足任一即触发：

- **余量下限**：最紧的那个窗口剩余 ≤ `switch_at_percent`（默认 10%）
- **提前量**：按实测燃烧速率，预计在 `lead_time_minutes`（默认 15 分钟）内耗尽。
  **这条不是锦上添花**——线上见过一个凭据 45 分钟从 84% 烧到 99%，按那个速度，10% 的余量只剩半小时，
  一分钟一次的检查也可能刚好跨过阈值。

  **但它有封顶（`projectionCeiling`，2 倍下限）**：不管烧多快，投影都不许退役余量高于
  `2 × switch_at_percent` 的凭据。**因为提前量按分钟算，而一分钟值多少百分点取决于当时的速度**——
  实测某车队 270 百分点/小时，15 分钟提前量就等于「余量掉到 67% 就换人」，
  下限那条规则从来没机会生效，每个凭据只用掉三四成窗口就被退役。

  封顶的依据是：投影本来只为盖住两次检查之间的盲区，而池子里的第二个成员已经让交接无感——
  跨过阈值的代价是**一次被代理吸收掉的 429**，不是断服。拿它换半个窗口的额度不划算。
- **失效**：上游已经不接受这个凭据了（401）

**但有一条反向规则**：如果绑定窗口的重置时间比预计耗尽还早，就**不换**——它会自己回血，
这时候换人纯粹是把上一个凭据的尾巴扔掉。

### 怎么选替补

三条规则，按顺序：

1. **先排除**：token 失效、已耗尽（且短期内不会重置）、余量本身就低于阈值（换了等于马上还要再换）、
   刚刚被换下来过、配置里点名不启用的。每一条排除理由都会显示在面板上，可以被质疑。
2. **按「能撑多久」排序**，而不是按剩余百分比。**一个百分点在不同套餐上不值一样的钱**——
   Plus 账号剩 100% 可能不如 Team 账号剩 40%。所以换算成美元：`剩余美元 ÷ 当前消耗速度`。
   这个换算只有本插件做得到，因为额度的美元估值本来就是它在算的。
3. **同时合格时，优先用更早作废的额度**。周窗口 9 小时后重置的那 60% 余量不用就没了；
   161 小时后才重置的留着不会浪费。**用完即失的先用。**

### 判定靠推算，探测只在真要动手时花

**闲置的凭据，额度只可能做两件事**：停在上次读数不动，或者窗口一到就归零。两件都是算术。
所以绝大多数情况下根本不需要问上游：

- **在服务的凭据**，每个响应都带额度头，插件本来就在记——读数天然是新的。
- **闲置的凭据**，用上次读数 + 重置时间推算。窗口已经过了重置点，就是满的；没过，就还是上次那个数。

**一次完整的轮换最多花 2 次探测**，而且都花在真要动手的那一刻：

1. **推算说在役凭据快耗尽时**，先探 1 次确认再动手——推算漂了的话，这一次探测省下的是一次没必要的轮换。
2. **替补真要顶上去之前**，探 1 次确认它还活着。这次是必要的：一个闲置期间被吊销的凭据，
   在推算里看起来完美无缺（正因为闲置，没人问过它），直接顶上去就是把失败甩给调用方。

**第三次探测：窗口重置之后对一次账。** `effectiveWindows` 是**推**出来窗口已经重置的（时钟过了重置点就算满），
这个推断原则上对，但值得跟上游核对一次——5 小时窗口一天不到 5 次，周窗口一周约 1 次。
它不看池子缺不缺人都会跑，因为它的职责是**让面板报的是观测到的东西，而不是几小时前推出来的东西**。
`resync_after_reset: false` 可以关掉，关掉后推断就自己说了算，一个请求都不发。

**预算是按额度周期算的**，记在 state.json 里，重启不会重置。再加一条每凭据每日硬上限
（`max_probes_per_day_per_credential`，默认 6）兜底。面板上直接显示「今日探测 N 次」——
正常情况下这个数**连着好几天都是 0**。

关于探测的三个实测结论：

- **最小请求几乎不耗额度**：连发两次，读数不动。
- **被拒绝的请求读不到额度**：模型名写错会 400，而 400 **不带**任何额度头，所以没有「免费探针」这条捷径。
- **429 照样带额度头**，所以打满的号也能读，不会变成盲区。

### 探测走凭据自己的出口

**这条是 2.4.0 修的一个真实缺陷。** CPA 给每个凭据配了独立出口（auth 文件里的 `proxy_url`），
正常请求和 token 刷新都认它，但**插件的 `host.http.do` 不认**——CPA 那边是
`h.newHTTPClient(nil)`，auth 写死 nil，于是退回宿主机自己的地址。

后果是：一个平时从洛杉矶出去的账号，被从芝加哥发认证请求。**这比探测频率高危险得多**，
因为它正好是风控要找的形状。而 `pluginapi.HTTPRequest` 里根本没有 proxy 字段，插件想指定也指定不了。

所以 2.4.0 起插件**自己拨号**：读凭据的 `proxy_url`，自己走 SOCKS5（支持用户名/密码），
出口和这个凭据的真实流量完全一致。**代理连不上就让探测失败，绝不退回直连**——
退回直连就是这个缺陷本身。

**另一条铁律**：上游明确拒绝过（401/403）的凭据**再也不探**，直到 access_token 变了
（说明有人重新登录过）。只有重新登录能改变答案，反复去问是这个插件能产生的最难看的流量。

### 护栏

- 默认关闭；`dry_run` 只决策不写入
- **永远先启用替补、再停用旧的**，绝不出现空池的瞬间（这条有专门的突变测试守着）
- 没有任何候选合格时，**保持现状并告警**，绝不因为找不到人就把当前凭据停掉
- `min_switch_gap_minutes` + `max_changes_per_day` 熔断，**手动触发也一样受限**——
  熔断器存在的意义就是防止快速造成损害，「这次是人点的」不构成例外
- 熔断计数随 state.json 持久化，重启不会把当天的额度重新花一遍
- `never_enable` / `never_disable` 名单
- 写回时用 `map[string]json.RawMessage` 整体透传，**不认识的字段一个不丢**；
  文档里没有 `refresh_token` 就直接拒绝写入
- 每次改动都进日志和面板

`POST /v0/management/codex-weekly-usd/rotate` 可以立刻评估一次（**只接受 POST**：这个路由会改状态，
不能靠点链接触发）。

`POST /v0/management/codex-weekly-usd/refresh` **强制重读所有凭据**。
自动路径全都要「有理由」才问上游——窗口过了重置点、池子缺人、替补要顶上去。
**额度被带外重置（比如人工给所有账号重置）不满足任何一条**：它不推进时钟、也不掏空池子，
所以自动机制永远不会发现，面板会一直报着那一刻起就不再成立的数字。
这条路由就是操作者说「你手上的数字是错的，去看一眼」。

它**绕过按周期的探测预算**（操作者问的是新问题，不是轮换器重复老问题），
但**不绕过每日上限，也不绕过「上游已拒绝的凭据不再探」**——那个答案只有重新登录能改变。

**一个已知限制**：长期停用的凭据，代理不会替它刷新 access_token，过期后探测会 401，看起来像失效。
这版只告警，不自动走 OAuth 刷新。

更要命的是 CPA 那一侧的连锁反应：`shouldRefresh()` 开头就是
`if hasUnauthorizedAuthFailure(a) { return false }`，而清除这个错误状态的两处代码都带
`if !auth.Disabled` 前提。**所以一个凭据只要 401 过一次然后被停用，它的错误状态就永远清不掉，
CPA 永远不会再为它刷新 token。** 这些状态不落盘，重启 CPA 可以清空。

因此 `disable_dead_tokens` 是把双刃剑：它省掉每个请求的一次无效尝试，但也会让一个**本来可能自愈的**
凭据永久卡死。区分方法看错误码——业务请求返回 `token_revoked` 可能是暂时的，
而刷新返回 `refresh_token_invalidated`（"Your session has ended"）是终态，只能重新登录。

### 面板报的是「现在」，不是「上次轮换那一刻」

两条以前会骗人的地方：

- **候选表是存下来的快照**，只在轮换器真正动手时才刷新。手动刷新页面什么也不会变，因为没有任何东西重算。
  现在**每次请求都现算**——排序已经是纯算术，不碰上游，没有理由缓存。
- **过了重置点的倒计时会被钳在 0**，然后一直停在那儿。于是面板一边显示几小时前就过期的截止时间，
  一边显示同一时刻起就不再成立的百分比。现在会**按整周期把重置点滚到未来**，
  并标记 `reset_inferred`——百分比原样保留（凭空编一个更糟），但会打上「待确认」，
  下一次对账用真实读数替换它。

## 面板

**界面支持中文 / English**，右上角切换，选择记在浏览器里。首次打开按浏览器语言自动选。
后端的告警是**结构化的**（code + 字段），不是现成的句子，所以切语言时告警也跟着切，
不会剩一半。

每个凭据一行：

- **额度 / 时间双进度条** —— 额度消耗与窗口时间流逝并排。谁烧太快，一眼就看出来。
- **节奏** —— `已用百分比 ÷ 时间流逝百分比`。>1.15 标「偏快」，<0.85 标「宽裕」。**大于 1 就意味着会在重置前用完。**
- **周额度 / 已用 / 剩余 / 日均**（美元），外加重置倒计时。
- **依据** —— 这个数字来自哪个估算器、背后有多少证据支撑。

展开任意一行，还有按模型的完整明细（请求数、失败数、输入输出 token 并标出推理子集、缓存命中率、所用价目、每次均价、金额）、该凭据的用量走势图，以及完整的推导过程：已归属 vs 挂账、两个估算器各自的值、校准样本数、整窗覆盖与否、续航天数与跑满预警。

页面顶部是[模型可用性](#模型可用性)看板，然后才是额度金额 —— 出事的时候先看到的应该是「什么坏了」。

全局还有汇总卡片（周额度总值、已用、剩余、实测消耗、缓存省下、请求与失败数）、走势图、生效价目表、排序和 JSON 导出。

### 图表

全部是内联 SVG，不引任何外部库，页面自包含。

- **用量走势** —— **图表覆盖一周**。柱状为每小时消耗（左轴），叠加**近 7 天滚动消耗折线**（自带右轴）。

  折线原来画的是「从图表起点累计」，那条线只会往上爬，**除了「时间过去了」以外什么都没说**。
  滚动窗口是平稳量：负载稳定就是平的，负载真的涨了才往上走，负载降了会掉下来。
  7 天是因为额度本身就是按周计的。

  左边一段画成虚线，表示那些点身后不足 7 天的数据，数字是偏低的——不是真的低，是**统计不全**。
  留存刻意开到 14 天（图表跨度的两倍），就是为了让每个可见的点身后都有完整一周。
- **额度曲线**（每个凭据）—— 已用百分比随时间的走势，配一条**匀速参考虚线**（把 100% 均摊到整个窗口）。**曲线高过虚线，就是「节奏 > 1」的可视化形态。**

额度曲线只画**当前窗口**：百分比下跌意味着窗口翻转，曲线从那里重新开始，否则会画成锯齿，而且参考线会锚在一个已经关闭的窗口上。只有一个读数时**什么都不画**，而不是给一张空图配一句承诺趋势的说明。

## 安装

### 插件商店

在 CLIProxyAPI 管理面板的插件商店里搜 `codex-weekly-usd` 安装。

### 手动

从 [Releases](https://github.com/tang12306/cpa-plugin-codex-weekly-usd/releases) 下载对应平台的包，把动态库放到：

```
<CLIProxyAPI 工作目录>/plugins/<goos>/<goarch>/codex-weekly-usd.so
```

**文件名必须等于插件 id。** 另外注意这个路径是相对 systemd 的 `WorkingDirectory` 解析的——如果 service 文件里没写 `WorkingDirectory=`，systemd 默认是 `/`，插件会被去 `/plugins/...` 里找，然后你会看到「已安装 0」。

### 价目

每天从 `https://models.dev/api.json` 的 openai provider 刷新，缓存到 `prices.json`，并内置一份表作为离线兜底。

**拉取优先走宿主的 HTTP 回调**（`host.http.do`），这样 CLIProxyAPI 里配好的代理会自动生效——网络受限环境不用再单独配一遍。宿主拒绝该回调时才退回直连。面板页脚会显示这次是「经 CPA 代理」还是「直连」。

没有公开价目的模型会单独计入 `unpriced_requests` 并给出告警——它们的花费是**缺失**，而不是被悄悄当成 0。

## 路由与鉴权

| 路由 | 鉴权 | 内容 |
|---|---|---|
| `/v0/resource/plugins/codex-weekly-usd/panel` | **无** | 不含数据的 HTML 壳 |
| `/v0/management/codex-weekly-usd/data` | 管理密钥 | 完整报表 |
| `/v0/management/codex-weekly-usd/prices` | 管理密钥 | 生效价目 |

CLIProxyAPI 的插件资源路由**不过管理鉴权**，所以本插件的面板刻意**不含任何数据**：它只是个壳，向使用者索取管理密钥后，自己去调带鉴权的路由。测试固化了这一点——面板返回 200 且不含任何凭据标识，`/data` 无密钥返回 401。

管理接口**只认 header**（`Authorization: Bearer` 或 `X-Management-Key`），不认 query 参数，所以浏览器无法直接打开受保护路由；这正是壳存在的理由。

## 数据文件

```
data_dir/
  state.json               每个凭据的累加器（原子写入）
  prices.json              价目缓存
  events/YYYY-MM-DD.jsonl  每请求一行，用于事后核对估算
```

`state.json` 和事件日志含有按凭据的用量，**不要提交进版本库**（`.gitignore` 已覆盖）。

## 从源码构建

CLIProxyAPI 的插件 ABI 是**纯 C ABI + JSON**，不是 Go 的 `plugin` 包。因此插件**不需要**和宿主的 Go 版本一致，也**完全不 import** CLIProxyAPI 模块。

```sh
make build        # 产出 codex-weekly-usd.so
make test         # 91 项断言
```

需要 Go（cgo，所以要 gcc/clang）、Python 3 和 Node（图表测试用）。

cgo 无法在没有目标工具链的情况下交叉编译，所以各平台由 GitHub Actions 在各自的原生 runner 上构建。

## 测试

`test/harness.c` 用 `dlopen` 加载 `.so`，通过**真实的 C ABI** 喂脚本化 JSON，因此不需要跑起一个 CLIProxyAPI 就能验算法。

场景是算术而非意见：每个请求恰好花费 $2.00（gpt-5.6-sol 官方价），百分比恰好走 1 点，所以答案**必须**是 $200。

覆盖：两个估算器互相印证、缓存 token 扣除、推理 token 不重复计费、未知模型被标记、带停机间隔的重启、窗口翻转、经宿主回调拉取价目、以及面板零泄露。

可用性部分另有一组：单模型冷却不影响同凭据的其它模型、成功请求提前解除冷却、截止时间取自打满的那个窗口、
额度用尽时的估计截止时间、普通失败不算冷却、跨凭据的容量统计与停用排除、单点凭据告警、重复 429 只记一次。
`HARNESS_AUTH_LIST` 让 harness 返回一份真实形状的凭据清单，否则「已停用」这条路径无从测起。

`test/test_charts.js` 把 SVG 生成函数**从插件真实返回的面板里**抠出来，喂 48 小时合成序列，逐坐标断言（柱数、滚动窗口在稳定负载下必须走平、虚实两段、每小时一个点、翻转重启、退化情况）——**测的就是浏览器拿到的那份字节**。
